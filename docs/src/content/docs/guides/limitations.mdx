import { Aside } from '@astrojs/starlight/components'

The generator targets the common case: object schemas, `$ref`s, `allOf` composition,
`additionalProperties` maps, enums, arrays, and scalar constraints, validated against 128 real-world
specs. A few OpenAPI features are not yet fully represented. The generated code is always valid PHP,
these are completeness gaps, not crashes, but for a schema that relies on them the generated class
can be incomplete. This page is honest about where that happens so you can plan around it.

<Aside type="note" title="oneOf / anyOf now emit union types">
  As of 0.4.0, `oneOf`/`anyOf` emit native PHP union type hints (and a variant
  docblock) wherever the members resolve to scalars or generated Data classes.
  The residual gap is object-union runtime hydration, which still needs a
  discriminator. See [oneOf and anyOf](#oneof-and-anyof-emit-union-types) below.
</Aside>

## allOf is merged

A schema composed with `allOf` is flattened: every member schema is merged into a single class.
Members may be inline objects or `$ref`s to other components, and members that themselves use
`allOf` are merged recursively. Each member's `properties` are unioned and the `required` lists are
concatenated and deduplicated.

```yaml
Extended_Price:
  allOf:
    - type: object
      properties:
        billingCurrency: { type: string }
    - $ref: '#/components/schemas/Price'
```

This generates an `ExtendedPriceData` class that carries `billingCurrency` plus every property
inherited from `Price`, with `rules()` covering all of them. When the same property name is defined
by more than one source, the value is resolved deterministically: a later `allOf` member overrides
an earlier one, and an explicit own-level property overrides every member. The first-seen position
is kept for ordering, so the class lists own properties, then the first member's, then the next, and
so on.

A `$ref` member that is also a component in its own right keeps its standalone class. So `Price`
above is still emitted as `PriceData` and is also merged into `ExtendedPriceData`.

## additionalProperties is represented as a typed map

Map-style schemas, an object whose keys are dynamic and whose values share a type, are represented
as a typed PHP `array`. laravel-data v4 has no first-class Map type, so an `array<string, X>` is the
correct representation. There are three forms.

**Typed scalar value.** A map whose values are a scalar schema becomes an `array` property with a
`@var array<string, int>` docblock and a wildcard value rule derived from the value schema. This is
the fully-enforceable case: the value constraints are validated per entry.

```yaml
Language:
  type: object
  additionalProperties:
    type: integer
```

A property whose schema is `$ref: Language` generates:

```php
/** @var array<string, int> */
public readonly ?array $language = null,
```

with rules `'language' => ['sometimes', 'array']` and `'language.*' => ['integer']`. A value schema
of `{ type: string, maxLength: 10 }` yields `'language.*' => ['string', 'max:10']`, so the value
constraints carry through verbatim.

**Untyped map (`additionalProperties: true`).** Becomes `@var array<string, mixed>` with a single
`['array']` rule and no per-value rule.

**`$ref` value.** A map of objects (for example `additionalProperties: { $ref: Price }`) becomes
`@var array<string, PriceData>` with `'field' => ['array']` and `'field.*' => ['array']`.

<Aside type="caution" title="$ref map values are neither validated nor auto-hydrated">
  laravel-data only auto-hydrates `DataCollection` elements and typed constructor parameters. The
  values of a `$ref`-valued map are typed in the docblock (`array<string, PriceData>`) but are
  **not** cast into `PriceData` instances at runtime, they arrive as raw arrays. Nor are the nested
  object values validated against the referenced schema's own `rules()`: the generated
  `'field.*' => ['array']` rule only asserts each value is array-shaped, not that it matches
  `Price`. So a `$ref`-valued map is validated to "a map of arrays" and the server hands you raw
  arrays. Hydrate and validate the entries yourself (`PriceData::from($value)` /
  `PriceData::validate($value)`) if you need typed, checked objects.
</Aside>

### Pure-map components

A component that is a pure map (`type: object` with only `additionalProperties` and no named
`properties`) is **not** emitted as its own Data class. Emitting an empty class would be a bug.
Instead the array type is inlined wherever the component is referenced, so a property of type
`$ref: Language` is generated directly as `array<string, int>`. The map is represented at every use
site, deterministically, with no empty wrapper class.

### Non-object alias components (scalar, array, oneOf/anyOf)

A top-level component that is itself a scalar (`Time: { type: string, format: date-time }`), an array
(`Tags: { type: array, items: { type: string } }`), or a `oneOf`/`anyOf` union
(`IntOrString: { oneOf: [{ type: integer }, { type: string }] }`) has **no** object `properties`, so it
is a **type alias**, not a Data class. Such a component is **not** emitted as an empty Data class.
Instead, every `$ref` to it resolves to the underlying type at the use site: a scalar alias becomes the
scalar PHP type plus the constraint it carries (a date-time alias still emits the date-time rule, a
length-bounded string alias its `max:`/`min:`), an array alias becomes the `array`/`DataCollection`
type its items imply, and a union alias becomes the native PHP union (or `mixed` for the messy cases,
per the usual `oneOf`/`anyOf` rules). Chained aliases (`A: { allOf: [{ $ref: B }] }` where `B` is itself
an alias) resolve transitively, with a cycle guard. The same resolution applies on the server scaffold:
a request/response `$ref` to such a component types against the underlying value rather than a missing
class, falling back to `Request`/`JsonResponse` when the underlying type is not a Data class.

A `type: object` component with no properties (or `properties: {}`) is a genuinely **empty object**, not
an alias, and **still** emits an (empty) Data class. The distinction is deliberate: only non-object
(scalar/array/composition) components are aliased.

### Mixed objects (named properties + additionalProperties)

When a schema declares both named `properties` and `additionalProperties`, the named properties are
emitted normally with full rules. The dynamic overflow (keys beyond the named ones) is **not**
captured: laravel-data cannot route unknown keys into a designated property without a custom cast, so
rather than emit a non-functional overflow field that silently fails to hydrate, the generated class
carries a docblock note that the dynamic keys are not captured. Read the known fields from the Data
object, and reach into the original payload for the overflow if you need it.

### additionalProperties: false

Standard Laravel has no rule to reject unknown keys on a nested data structure, so
`additionalProperties: false` is **not enforced** by the generated `rules()`. The named properties
are generated as usual; extra keys simply are not rejected. Enforce closed objects in your own
validation layer if you need that guarantee.

### Empty map encoding (a known issue)

An **empty** `additionalProperties` map currently serializes as a JSON array `[]`, not an object
`{}`. PHP cannot distinguish an empty associative array from an empty list, so `json_encode([])`
emits an array. Non-empty maps encode correctly as objects, and a `null` value stays `null`. A strict
client expecting `Record<string, string>` would receive an array for the empty case. This was
surfaced by the cross-language [end-to-end demo](/guides/end-to-end-demo) and is tracked as a
candidate fix (a cast that forces object encoding even when the map is empty).

## oneOf and anyOf emit union types

A property whose schema uses `oneOf` or `anyOf` emits a native PHP union type hint plus a `@var`
docblock listing the variants, whenever every member resolves to a clean PHP type: a scalar
(`string`, `int`, `float`, `bool`) or a generated Data class. `oneOf` and `anyOf` are handled
identically for typing, since PHP cannot distinguish "exactly one" from "at least one" shape.

```yaml
animal:
  oneOf:
    - $ref: '#/components/schemas/Cat'
    - $ref: '#/components/schemas/Dog'
```

This generates:

```php
/** @var CatData|DogData */
public readonly CatData|DogData|null $animal = null,
```

The union is built in source order, deduplicated, with `null` forced to the end. `null` is added to
the union (and the property defaults to `= null`) when any member is the `null` type, any member is
itself nullable, or the property is nullable. A scalar union such as `oneOf: [string, integer]`
becomes `string|int`.

### Fallback to mixed

When a member does **not** resolve to a clean type, the whole property falls back to the previous
behavior: `public readonly mixed $payload` with presence-only rules. This is deliberate and
deterministic. It happens when a member is itself a `oneOf`/`anyOf`, an array, a map, an inline
object, an untyped or empty schema, an enum, or a `$ref` to something that is not a Data class.

### Rules stay presence-only

The generated `rules()` keep presence semantics (`required` / `sometimes` / `nullable`). They do
**not** assert which variant was supplied: standard Laravel validation cannot enforce "exactly one
of these shapes" without a discriminator, and a type rule on a union would wrongly reject a valid
variant. If you have a `discriminator` in the spec, it is noted but not wired into runtime dispatch.

This applies to **scalar** unions too. A `oneOf: [string, integer]` (or the JSON Schema multi-type
form `type: ["string", "integer"]`) emits the `string|int` type hint but only a presence rule, with
**no per-variant type rule**. The native PHP union already constrains the value to one of the member
types at hydration, but the validator does not separately assert "this is a string OR an integer".
A field whose only constraint is being one of several scalar types is therefore validated for
presence only. If you need to reject, say, a boolean on a `string|int` field at the validation layer,
add a rule for it yourself.

### Object-union runtime hydration still needs a discriminator

The union type hint and docblock are a typing, IDE, and PHPStan improvement. Scalar unions
(`string|int`) hydrate fine through spatie/laravel-data. An **object union** (`CatData|DogData`),
however, does not auto-hydrate: spatie/laravel-data cannot pick which Data class to instantiate from
a raw payload without a discriminator or a custom cast. So while the type hint is correct and useful
for static analysis, at runtime an object-union property arrives as a raw array unless you supply a
discriminator-aware cast yourself.

**Workaround for object unions.** Hydrate the chosen variant yourself after the Data object is
constructed, keyed off a discriminator field your spec already carries. Given a spec like:

```yaml
animal:
  oneOf:
    - $ref: '#/components/schemas/Cat'
    - $ref: '#/components/schemas/Dog'
  discriminator:
    propertyName: kind   # each variant carries a "kind" field: "cat" or "dog"
```

the generated property is typed `CatData|DogData|null`, but at runtime `$pet->animal` arrives as a
raw `array`. Dispatch on the discriminator in your controller or service:

```php
$raw = $pet->animal;                        // raw array, e.g. ['kind' => 'cat', 'lives' => 9]

$animal = match ($raw['kind'] ?? null) {    // the spec's discriminator propertyName
    'cat'   => CatData::from($raw),
    'dog'   => DogData::from($raw),
    default => throw ValidationException::withMessages([
        'animal' => 'Unknown animal variant.',
    ]),
};

// $animal is now a fully hydrated CatData or DogData
```

If your spec has no discriminator, sniff a distinguishing field instead (for example a property only
`CatData` defines), or register a custom cast on the property. Scalar unions (`string|int`) need none
of this: they hydrate directly.

## String formats: some are no-ops

A `format` on a string is mapped to the closest Laravel rule where one exists. `email`/`idn-email`
become `email`, `uuid` becomes `uuid`, `uri`/`url`/`iri` become `url`, and `ipv4`/`ipv6`/`ip` map to
the matching IP rule. Date formats are mapped strictly: `date` becomes `date_format:Y-m-d` (a bare
calendar date, a timestamp is rejected) and `date-time` becomes a dedicated RFC3339 rule that accepts
the `Z`, numeric-offset, and fractional-second timestamp forms and rejects a bare date.

The following string formats are **intentionally not validated** and emit only the base `string` rule
(or no extra rule): `hostname` / `idn-hostname`, `byte`, `binary`, and `password`. Laravel has no
faithful built-in for them, and a hand-rolled regex would be either too loose to add value or too
strict and wrongly reject valid input, so they are treated as plain strings. The value still arrives
and round-trips, it is simply not format-checked. Add your own rule if you need to enforce one of
these.

## Numeric constraints

Inclusive `minimum`/`maximum` emit `min:`/`max:`. The exclusive forms emit `gt:`/`lt:`, covering both
the OpenAPI 3.0 boolean companion (`minimum: N` with `exclusiveMinimum: true`) and the 3.1 numeric
keyword (`exclusiveMinimum: N`). `multipleOf` is enforced with a small reusable `MultipleOfRule`
(Laravel has no native rule for it), and array `uniqueItems: true` adds a `distinct` rule on the
items. Numeric `enum` values, including floats, emit a `Rule::in([...])` constraint; a top-level
number-enum component (which cannot be a PHP backed enum) becomes a single-`value` Data class that
carries that constraint rather than an empty class.

## const is a single-value enum

A schema with `const` (OpenAPI 3.1 / JSON Schema) pins a value to one literal. The generator treats
it as a one-value enum: the property keeps its concrete type and gains a single-value `Rule::in`
constraint.

```yaml
version:
  type: string
  const: v1
```

This generates `public readonly ?string $version` with `'version' => ['sometimes', Rule::in(['v1'])]`.
A bare `const` with no declared `type` infers its PHP type from the literal (`const: v1` is a
`string`, `const: 3` is an `int`). Only scalar `const` values (string and integer) are enforced this
way; an array, object, boolean, or null `const` falls back to the normal type handling.

## this is the one renamed property

PHP allows every reserved word (`for`, `class`, `list`, `match`, ...) as a parameter variable name,
so a property named after a keyword keeps that name. The single exception is `this`: `$this` is
illegal as a parameter. A property literally named `this` is emitted as `$_this` with a
`#[MapName('this')]` attribute, so the original wire key still round-trips on (de)serialization.

## Security: specs are untrusted input

The generator reads an OpenAPI spec and writes PHP source that your application then loads and
executes. Treat the spec as untrusted input: a hostile spec can try to inject PHP through any
spec-derived value that lands in generated code (a class name, a string literal, a docblock, a
validation rule). The generator defends against this, but operators still own a few boundaries.

**Docblock injection is neutralized.** Free text from the spec (operation summaries, paths) is
written into generated controller docblocks. Before that, every `*/` is rewritten to `* /` so a
value cannot close the comment early and inject code, and newlines and other control characters are
collapsed to a single space so a value cannot forge extra doc lines. The same neutralization applies
to any spec free text that reaches a comment in the controller or route output.

**Namespace and class-name options are validated.** The `--namespace`, `--suffix`, and
`--controller-namespace` options (and their `config` equivalents) are interpolated raw into
generated `namespace ...;` declarations and class names. They are validated at startup, before any
file is written: a namespace must be a legal PHP namespace and a suffix must be a legal PHP
identifier. An invalid value fails fast with a clear error and a non-zero exit, rather than emitting
broken or injected PHP. This also rules out accidental breakage such as a stray space.

**Validation patterns are never silently dropped.** A `pattern` constraint is emitted as a Laravel
`regex:` rule. The generator picks a PCRE delimiter not present in the pattern from a candidate list,
and if a pattern somehow contains all candidates it falls back to a fixed delimiter and escapes it
rather than dropping the rule. A field is never silently left under-validated.

**Non-OpenAPI documents are rejected.** A Swagger 2.0, non-3.x, or empty document is rejected with a
clear error naming what was found, instead of silently parsing into an empty result.

**Output paths must be operator-controlled.** The output directory, controller path, and routes path
are written exactly where you point them, by design, with no sandboxing. Never derive these paths
from untrusted input (for example from spec content or from an end user). Point them at fixed,
operator-controlled locations.

**YAML resource exhaustion: use OS-level limits.** YAML anchors and aliases are expanded by the
underlying parser before the generator sees the data, a classic "billion laughs" / alias-bomb
vector that the vendored library cannot disable. The generator applies a cheap pre-parse input-size
guard (default 24 MiB, configurable via `max_bytes` / `--max-bytes`) that caps the blast radius and
sits well above the largest real-world specs. This bounds input size but not expansion depth, so when
running against genuinely untrusted specs you should still run the generator under OS-level resource
limits (memory and CPU, for example via `ulimit` or a container quota).

## What is not affected

Everything else generates fully: object schemas with `properties`, `$ref`s between schemas,
`allOf` composition (merged into a flat class), `additionalProperties` maps (typed `array` with
per-value rules), nested objects and arrays (`DataCollection`), native enums, the read/write variant
split, scalar constraints (`minLength`, `maxLength`, `pattern`, `format`, `minimum`/`maximum`,
`enum`), the server scaffold, and `oneOf`/`anyOf` union type hints where the members resolve. The
spec-derived validation is presence-exact, with the caveats noted above: object-union runtime
hydration needs a discriminator, and the map caveats apply (raw-array `$ref` map values, uncaptured
mixed-object overflow, unenforced `additionalProperties: false`).
