---

The generator targets the common case: object schemas, `$ref`s, `allOf` composition, enums,
arrays, and scalar constraints, validated against 128 real-world specs. A few OpenAPI features are
not yet fully represented. The generated code is always valid PHP, these are completeness gaps, not
crashes, but for a schema that relies on them the generated class can be incomplete. This page is
honest about where that happens so you can plan around it.

<Aside type="caution" title="Scheduled for 0.3.0">
  Representing `additionalProperties` and improving `oneOf`/`anyOf` are the remaining items for the
  next release. See the [roadmap](/roadmap) for the plan.
</Aside>

## allOf is merged

A schema composed with `allOf` is flattened: every member schema is merged into a single class.
Members may be inline objects or `$ref`s to other components, and members that themselves use
`allOf` are merged recursively. Each member's `properties` are unioned and the `required` lists are
concatenated and deduplicated.

```yaml
Extended_Price:
  allOf:
    - type: object
      properties:
        billingCurrency: { type: string }
    - $ref: '#/components/schemas/Price'
```

This generates an `ExtendedPriceData` class that carries `billingCurrency` plus every property
inherited from `Price`, with `rules()` covering all of them. When the same property name is defined
by more than one source, the value is resolved deterministically: a later `allOf` member overrides
an earlier one, and an explicit own-level property overrides every member. The first-seen position
is kept for ordering, so the class lists own properties, then the first member's, then the next, and
so on.

A `$ref` member that is also a component in its own right keeps its standalone class. So `Price`
above is still emitted as `PriceData` and is also merged into `ExtendedPriceData`.

## additionalProperties is not represented yet

Map-style schemas, an object whose keys are dynamic and whose values share a type, are not
modelled. The dynamic key/value shape is dropped.

```yaml
Language:
  type: object
  additionalProperties:
    type: integer
```

Today this generates an empty `LanguageData` class with no way to hold the arbitrary
string-to-integer entries.

**Workaround for now:** treat such payloads as a plain `array` in your own code, or define the
known keys explicitly as properties where that is possible.

## oneOf and anyOf are typed as mixed

A property whose schema uses `oneOf` or `anyOf` is generated as `mixed`, with presence-only
validation. The individual variant types are not enforced, and the generated `rules()` cannot
assert which variant was supplied.

```yaml
payload:
  oneOf:
    - type: string
    - type: object
```

Today this generates `public readonly mixed $payload` with `'payload' => ['required']`.

This is a deeper limitation than the previous two: without a discriminator, PHP and Laravel
validation cannot enforce "exactly one of these shapes" at request-validation time. A future
release may emit a union type hint where the variants resolve cleanly, but runtime variant
validation will always require a discriminator in the spec.

**Workaround for now:** validate the variant shape in your own controller or service layer after
the Data object is hydrated.

## What is not affected

Everything else generates fully: object schemas with `properties`, `$ref`s between schemas,
`allOf` composition (merged into a flat class), nested objects and arrays (`DataCollection`),
native enums, the read/write variant split, scalar constraints (`minLength`, `maxLength`,
`pattern`, `format`, `minimum`/`maximum`, `enum`), and the server scaffold. If your schemas avoid
the two features above (`additionalProperties` and `oneOf`/`anyOf`), the output is complete and the
spec-derived validation is exact.
