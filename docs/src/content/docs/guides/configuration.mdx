Publish the config file to set defaults you commit to your repo:

```bash
php artisan vendor:publish --tag=openapi-laravel-config
```

This writes `config/openapi-laravel.php`:

```php
<?php

declare(strict_types=1);

return [

    /*
     * Path to the OpenAPI document (YAML or JSON) used as the source of truth.
     */
    'spec' => env('OPENAPI_LARAVEL_SPEC', base_path('openapi.yaml')),

    /*
     * Where generated classes are written, and the namespace they live under.
     */
    'output' => [
        'path' => app_path('Data'),
        'namespace' => 'App\\Data',

        /*
         * Suffix appended to generated Data class names (e.g. Customer ->
         * CustomerData). Enums are never suffixed. Set to '' to disable.
         */
        'suffix' => 'Data',

        /*
         * Delete existing *.php files in the output directory before writing,
         * so a removed schema does not leave a stale class behind.
         */
        'prune' => false,
    ],

    /*
     * Maximum schema nesting depth the parser will follow before bailing out.
     * Guards against pathological or maliciously deep specs.
     */
    'max_depth' => 64,

    /*
     * Maximum raw spec file size, in bytes, accepted before parsing. The spec is
     * untrusted input fed to a YAML parser that expands anchors/aliases before we
     * see it, so a pre-parse size guard caps the alias-bomb blast radius. The
     * default (24 MiB) sits well above the largest real-world specs.
     */
    'max_bytes' => 25_165_824,

    /*
     * Server scaffold: generate one abstract controller per OpenAPI tag,
     * with one abstract method per operation, typed by the generated Data classes.
     * Enabled by default. Disable with 'enabled' => false or pass --no-controllers.
     */
    'controllers' => [
        'enabled'   => true,
        'path'      => app_path('Http/Controllers/Api'),
        'namespace' => 'App\\Http\\Controllers\\Api',
    ],

    /*
     * Server scaffold: generate a routes file with one Route:: entry per operation.
     * Enabled by default. Disable with 'enabled' => false or pass --no-routes.
     */
    'routes' => [
        'enabled' => true,
        'path'    => base_path('routes/api.generated.php'),
    ],

];
```

## Options

### `spec`

Path to the OpenAPI document (YAML or JSON) used as the source of truth. Defaults to `base_path('openapi.yaml')`, and reads the `OPENAPI_LARAVEL_SPEC` environment variable if set.

The `--spec` flag on the artisan command and the standalone binary overrides this value.

### `output.path`

Directory the generated classes are written to. Defaults to `app_path('Data')`, that is `app/Data`. Overridden by the `--output` flag.

### `output.namespace`

PHP namespace the generated classes live under. Defaults to `App\Data`. Keep this aligned with `output.path` so the autoloader resolves the classes. Both the artisan command and the standalone binary accept a `--namespace` flag that overrides this value per run (the binary can also read it from [`openapi-laravel.json`](#standalone-binary-openapi-laraveljson)).

### `output.suffix`

Suffix appended to generated Data class names, so a `Customer` schema becomes `CustomerData`. Defaults to `Data`. Enums are never suffixed. Set it to an empty string (`''`) to disable the suffix entirely.

<Aside type="caution">
  Disabling the suffix can cause a Data class and the enum it references to collide on the same
  name (for example a `Status` object and a `Status` enum). The naming layer resolves collisions,
  but keeping the suffix is the simplest way to avoid them.
</Aside>

### `output.prune`

When `true`, deletes existing `*.php` files in the output directory before writing, so a schema you removed from the spec does not leave a stale class behind. Defaults to `false`.

<Aside type="caution">
  Pruning deletes files. Only point `output.path` at a directory that holds nothing but generated
  output, and rely on version control to review what was removed.
</Aside>

### `max_depth`

Maximum schema nesting depth the parser follows before it bails out. Defaults to `64`. This guards against pathological or maliciously deep specs that would otherwise recurse without bound. Raise it only if you have a legitimately deeply nested spec and trust its source.

### `max_bytes`

Maximum raw spec file size, in bytes, accepted before parsing. Defaults to `25_165_824` (24 MiB). The spec is untrusted input fed to a YAML parser that expands anchors and aliases before the generator sees the data, a classic alias-bomb vector the underlying parser cannot disable. This pre-parse size guard caps the blast radius and sits well above the largest real-world specs. Overridden by the `--max-bytes` flag. Raise it only for trusted inputs, and prefer OS-level resource limits when running against genuinely untrusted specs. See the [limitations page](/guides/limitations#security-specs-are-untrusted-input) for the full threat model.

### `controllers`

Controls the server scaffold: abstract controller generation. All three sub-keys are optional.

| Key         | Default                            | Description                                                                 |
| ----------- | ---------------------------------- | --------------------------------------------------------------------------- |
| `enabled`   | `true`                             | Generate abstract controllers. Overridden by `--controllers` / `--no-controllers`. |
| `path`      | `app_path('Http/Controllers/Api')` | Directory the abstract controller files are written to.                     |
| `namespace` | `'App\\Http\\Controllers\\Api'`   | PHP namespace for the generated abstract controllers.                       |

When enabled, the generator writes one `Abstract{Tag}Controller` file per OpenAPI tag into `path`. Each file is overwritten on every run. Your concrete controllers (which extend the abstract classes) are never touched.

<Aside type="note">
  `--no-controllers` skips controller generation for one run regardless of the config;
  `--controllers` forces it on when the config disables it. See
  [precedence](#precedence-flags-beat-config-config-beats-defaults).
</Aside>

### `routes`

Controls the server scaffold: routes file generation.

| Key       | Default                                     | Description                                                           |
| --------- | ------------------------------------------- | --------------------------------------------------------------------- |
| `enabled` | `true`                                      | Generate the routes file. Overridden by `--routes` / `--no-routes`.   |
| `path`    | `base_path('routes/api.generated.php')`     | Path the generated routes file is written to.                         |

The generated file contains one `Route::{method}(...)` call per operation, referencing the concrete controller class by tag name. It is overwritten on every run.

<Aside type="note">
  `--no-routes` skips the routes file for one run regardless of the config; `--routes` forces it on
  when the config disables it. See
  [precedence](#precedence-flags-beat-config-config-beats-defaults).
</Aside>

See the [server scaffold guide](/guides/server-scaffold) for a complete worked example.

## Precedence: flags beat config, config beats defaults

Every setting resolves through the same three layers, for `openapi:generate`, `openapi:check`, and
the standalone binary alike:

```
command-line flags          (one run)
        ↓ override
config file                 (your committed defaults)
        ↓ override
built-in defaults           (full output: controllers and routes enabled)
```

For the scaffold toggles this means: `--controllers` / `--routes` force generation on even when the
config says `enabled => false`, and `--no-controllers` / `--no-routes` skip it even when the config
says `enabled => true`. Passing an enable flag together with its disable flag (for example
`--controllers --no-controllers`) is a configuration error: `openapi:generate` fails with a clear
message and `openapi:check` exits `2`.

The output **namespace** follows the same chain: `--namespace`, then `output.namespace` in the
config file, then the built-in default `App\Data`.

## Standalone binary (`openapi-laravel.json`)

The standalone binary reads an optional JSON config file: `openapi-laravel.json` in the working
directory, or any path given via `--config=<path>`. Its keys mirror `config/openapi-laravel.php`
one to one:

```json
{
  "spec": "openapi.yaml",
  "output": {
    "path": "src/Data",
    "namespace": "Acme\\Dto",
    "suffix": "Data",
    "prune": false
  },
  "controllers": {
    "enabled": true,
    "path": "src/Http/Controllers",
    "namespace": "Acme\\Http\\Controllers"
  },
  "routes": {
    "enabled": true,
    "path": "src/routes/api.generated.php"
  },
  "max_depth": 64,
  "max_bytes": 25165824
}
```

Every key is optional, and flags override the file per value (the same
[precedence](#precedence-flags-beat-config-config-beats-defaults) as the artisan commands). The file
is validated strictly before anything is generated: malformed JSON, an unknown key, or a wrong value
type fails with a clear message and no file is written, and namespaces from the file go through the
same identifier validation as the flags.

When neither the flags nor the file set a scaffold path, the binary derives deterministic defaults
relative to the model output directory: controllers go to `<output>/Controllers` and the routes
file to `<output>/routes.php`.
