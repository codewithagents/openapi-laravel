`openapi-laravel` has shipped **v1 (models)** and **v2 (server scaffold)**. This page is the honest account of what is in each version, what is deliberately basic, and what is planned next.

## v0.1.x: models

Spec in, generated `app/Data/*` out:

- One `laravel-data` class per `components.schemas` entry, plus per inline request and response shape.
- An explicit `rules()` method per class, derived from spec constraints: `required` / `nullable`, types, string `minLength` / `maxLength` / `pattern` / `format` (email, uuid, date, date-time, url, ip), numeric `minimum` / `maximum`, array `minItems` / `maxItems`, and enum via `Rule::enum` or `Rule::in`.
- Native backed enums for string and integer enums.
- `readOnly` / `writeOnly` handling: a read variant and a write variant, only when the spec uses the flags.
- Nested objects become nested Data classes; arrays become typed collections with `#[DataCollectionOf]`.
- A naming layer: StudlyCaps classes, camelCase properties with `#[MapName]` when the wire name differs, collision handling, and PHP reserved-word escaping.
- Two ways to run it: `php artisan openapi:generate` via the service provider, and a framework-free `vendor/bin/openapi-laravel` for non-Laravel CI.
- Determinism: the same spec in produces byte-identical files out.

## v0.2.0: server scaffold

The server scaffold feature is built and committed toward the 0.2.0 tag. It is opt-in (disabled by default):

- A generated abstract controller per tag: one abstract method per operation, typed by the v1 Data classes. An unimplemented operation is a PHP fatal, not silent drift.
- A generated routes file (`routes/api.generated.php`): one `Route::` entry per spec operation, pointing at the concrete controller class the user writes.

Pass `--controllers` and/or `--routes` to enable it, or set `controllers.enabled` and `routes.enabled` in the config file. See the [server scaffold guide](/guides/server-scaffold) for the full walkthrough.

## Supported composition

**`allOf` is merged.** A schema composed with `allOf` is flattened: every member schema (inline
objects and `$ref`s, recursively, including the schema's own `properties`) is merged into one Data
class, with `required` lists unioned and validation rules covering the combined shape. Conflicts are
resolved deterministically (a later member overrides an earlier one, an own-level property overrides
every member). A `$ref` member keeps its standalone class as well. See the [limitations
page](/guides/limitations) for details.

**`additionalProperties` is a typed map.** A map-style schema becomes a typed `array`: a scalar
value schema generates `array<string, int>` with a per-value wildcard rule (so value constraints are
enforced), `additionalProperties: true` generates `array<string, mixed>`, and a `$ref` value
generates `array<string, PriceData>`. A pure-map component is inlined at its use sites rather than
emitted as an empty class. Caveats (raw-array `$ref` map values, uncaptured mixed-object overflow,
unenforced `additionalProperties: false`) are on the [limitations page](/guides/limitations).

**`oneOf` / `anyOf` emit union types.** A property typed via `oneOf` or `anyOf` emits a native PHP
union type hint plus a `@var` variant docblock, whenever every member resolves to a scalar or a
generated Data class: `oneOf: [string, integer]` becomes `string|int`, and
`oneOf: [Cat, Dog]` becomes `CatData|DogData`. `null` is folded into the union (with a `= null`
default) when a member is the null type, a member is nullable, or the property is nullable. Messier
unions (a nested `oneOf`, an array, a map, an untyped or enum member) fall back deterministically to
`mixed` with presence-only rules. The server scaffold types a response that is a `oneOf`/`anyOf` of
Data-class `$ref`s as a Data-class union return, and otherwise keeps the `JsonResponse` fallback.

## Known limitations

<Aside type="note" title="oneOf / anyOf object-union hydration needs a discriminator">

- **`oneOf` / `anyOf`** now emit union type hints and variant docblocks with presence rules. The
  rules stay presence-only (no variant enforcement): standard Laravel cannot assert "exactly one
  shape" without a discriminator.
- **Object-union runtime hydration** (`CatData|DogData`) still needs a discriminator or a custom
  cast. The union type hint is a typing, IDE, and PHPStan improvement; scalar unions hydrate fine,
  but an object union arrives as a raw array at runtime without a discriminator-aware cast.

</Aside>

The generated code is always valid PHP. The [limitations page](/guides/limitations) has examples,
the fallback rules, and the object-union workaround.

## v0.4.0: oneOf / anyOf union typing (landed)

`allOf` merging and `additionalProperties` maps landed earlier. `oneOf` / `anyOf` union typing is
the headline of 0.4.0: native PHP union type hints and variant docblocks where the members resolve
cleanly, a deterministic `mixed` fallback otherwise, and Data-class union return types in the server
scaffold. Runtime variant validation and object-union hydration still depend on a discriminator being
present in the spec.

## Later: v3 (maybe)

Client generation built on the `Http::` facade. Less differentiated than the server scaffold, so it is a decide-later item rather than a commitment.
