This guide takes you from a spec file to generated Data classes. There are two ways to run the generator: the **artisan command** inside a Laravel app, and the **standalone binary** for anything else.

## In a Laravel app

<Steps>

1. **Install the runtime peer and the generator.**

   The generated classes extend `Spatie\LaravelData\Data`, so `spatie/laravel-data` v4 is a runtime
   dependency of your app. Without it, a fresh app hits fatal autoload errors as soon as it loads a
   generated class. The generator itself is a dev dependency.

   ```bash
   composer require spatie/laravel-data:^4.0
   composer require --dev codewithagents/openapi-laravel
   ```

2. **Generate from your spec.**

   ```bash
   php artisan openapi:generate --spec=openapi.yaml --output=app/Data
   ```

   The output namespace comes from `config/openapi-laravel.php` (`output.namespace`, default
   `App\Data`); the artisan command has no `--namespace` flag, so set it in the config if you need a
   different namespace. Set `spec` and `output.path` there too and you can then just run:

   ```bash
   php artisan openapi:generate
   ```

3. **Review and commit the output.**

   The command writes one Data class per schema (plus enums and write variants where the spec needs them) into your output directory. Read the diff, commit it, and use the classes in your controllers and services.

</Steps>

## Without Laravel (standalone binary)

Not a Laravel project, or running in a CI step that has no app bootstrapped? The same generator ships as a framework-free binary:

```bash
vendor/bin/openapi-laravel --spec=openapi.yaml --output=src/Data --namespace="Acme\\Dto"
```

| Flag          | Description                                              |
| ------------- | ------------------------------------------------------- |
| `--spec`      | Path to your OpenAPI 3.x document (YAML or JSON)         |
| `--output`    | Directory the generated files are written to            |
| `--namespace` | PHP namespace for the generated classes                 |

<Aside type="note">
  The binary and the artisan command share the same generator core, so the output is identical.
  The binary just skips the Laravel bootstrap and reads its options from flags instead of the config
  file.
</Aside>

## What you get

For a `Customer` schema that references a `CustomerStatus` enum, the generator writes:

```
app/Data/CustomerData.php      laravel-data class with a spec-derived rules() method
app/Data/CustomerStatus.php    native backed enum
```

If the spec marks fields with `readOnly` or `writeOnly`, you also get a write variant such as `CustomerWritableData.php`. See [generated output](/guides/generated-output) for full examples.

## Also scaffold controllers and routes

Once you have Data classes in place, you can generate abstract controllers and a routes file from the same spec. Pass `--controllers --routes` to the command:

```bash
php artisan openapi:generate --controllers --routes
```

This writes one `Abstract{Tag}Controller` per OpenAPI tag and a `routes/api.generated.php` file. You then extend each abstract controller with your own concrete implementation. See the [server scaffold guide](/guides/server-scaffold) for the full walkthrough.
