Hand-written DTOs, validation rules, and controllers drift from the API contract silently. Nobody notices the missing `nullable`, the renamed wire field, or the new enum case until production rejects a valid payload, or a consumer files the bug for you. The spec already states every one of those shapes; the drift exists only because humans re-type them.

`openapi-laravel` makes the spec the source of truth and regeneration the sync mechanism. It reads an OpenAPI 3.0 or 3.1 document (3.2 generates on a best-effort path with loud warnings, see [supported versions](/guides/openapi-versions)) and, out of the box, generates [spatie/laravel-data](https://github.com/spatie/laravel-data) classes with explicit, spec-derived `rules()` methods, native PHP enums, one abstract controller per tag, and a routes file, with typed and validated query, path, and header parameters and typed request and response bodies. The output is readable, deterministic PHP that lives in your repo and looks like code you would have written yourself.

## Spec-first, not code-first

The Laravel ecosystem is full of code-first tools that generate an OpenAPI document from your controllers and annotations. This tool goes the other way: the spec is the contract, and your models derive from it.

```
openapi.yaml  →  openapi-laravel  →  app/Data/*.php                       (laravel-data classes, rules(), enums)
(the contract)    (the generator)     app/Http/Controllers/Api/Abstract*  (one abstract controller per tag)
                                      routes/api.generated.php            (one route per operation)
```

When the spec changes, you re-run the generator and review the diff. There is no second source of truth to keep aligned by hand, and the [drift gate](/guides/drift-check) (`openapi:check`) fails CI if anyone forgets.

## What it generates

### Models and validation rules

- **Objects** become `laravel-data` classes with promoted, readonly constructor properties.
- **Validation** becomes an explicit `rules()` method derived from the spec: `required` / `nullable`, types, string `max` / `min` / `pattern` / `format` (email, uuid, date, url, ip), numeric `min` / `max`, array `min` / `max` items, and `Rule::enum` / `Rule::in`.
- **Enums** become native PHP backed enums (string or int).
- **Naming** maps spec names to StudlyCaps classes and camelCase properties, with `#[MapName]` when the wire name differs, plus reserved-word and collision handling.
- **Nested objects** become nested Data classes; **arrays** become `#[DataCollectionOf]` typed collections.
- **Nullability** is handled for both 3.0 `nullable` and 3.1 `type: [..., 'null']`.
- **readOnly / writeOnly** produce a read variant and a write variant, only when the spec uses the flags.
- **Composition** is handled: `allOf` is merged into one flat class, `additionalProperties` becomes a typed map (`array<string, X>`) with per-value rules, and `oneOf` / `anyOf` emit native PHP union types for scalars (`string|int`); a discriminated object union is validated and hydrated via an abstract morphable base, with a deterministic `mixed` fallback for the messy cases. See the [limitations guide](/guides/limitations) for the exact behaviour and residuals.

### Server scaffold: controllers and routes

The same run also produces, by default:

- **One abstract controller per tag**, with one abstract method per operation typed by the Data classes. An unimplemented operation is a PHP fatal, not silent drift.
- **A routes file** (`routes/api.generated.php`): one `Route::` entry per operation, pointing at the concrete controller you extend.
- **Typed, validated inputs and outputs**: per-operation `QueryData` / `PathData` / `HeaderData` classes enforce a parameter's spec constraints at runtime (a bad value is a 422, not a silent 200), request bodies (inline JSON, multipart, form-urlencoded, and component `$ref`) are typed Data params, and object response schemas become typed returns. See the [server scaffold guide](/guides/server-scaffold).

Want models only? Opt out with `--no-controllers --no-routes` or via `controllers.enabled` / `routes.enabled` in the config. See the [server scaffold guide](/guides/server-scaffold) for the full walkthrough.
